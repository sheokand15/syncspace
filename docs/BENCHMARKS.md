# Benchmarks

No measurements have been run yet. `tests/benchmarks/sync-latency.mjs` measures an authenticated two-client workload against a running SyncSpace service. Configure `SYNCSPACE_URL`, `SYNCSPACE_EMAIL`, `SYNCSPACE_PASSWORD`, and `SYNCSPACE_DOCUMENT_ID`; `SYNCSPACE_BENCH_SAMPLES` defaults to 1000. Run `npm run benchmark:sync`. It reports the edit-creation-to-peer-Y.Doc-visibility latency using one process's monotonic `performance.now()` clock, so clock synchronization is unnecessary. The receiver only observes the update after the collaboration server's PostgreSQL commit and broadcast.

The current script does not yet capture CPU, memory, database resource use, reconnection time, or more than two concurrent clients; these remain benchmark extensions. For broader runs, the reproducible target is 2, 10, and 50 clients; 10 KB and 100 KB starting documents; seeded insert/format workload; 5 minute warm-up plus 10 minute sample; controlled local network first, then report network conditions. Record Node version, hardware, database configuration, client count, update rate, failure count, CPU, memory, database usage, persistence throughput, and reconnect recovery time.

Synchronization latency is source edit creation to the first receiving client observing the corresponding state. Prefer same-process monotonic timing in a controlled harness or explicitly characterize clock offset for cross-machine tests. Collect at least 1000 observations for p50/p95; report p99 only with at least 10,000 observations and disclose limitations. Never present unrun targets as measured results.
